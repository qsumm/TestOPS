# 从旧版本升级（v1.8.x → v1.9.0）

> 本文档聚焦 v1.8.x → v1.9.0 的**变化与坑**；升级的完整流程（Pre-check / 执行 / Post-check / 回滚）见 **[升级SOP](升级SOP.md)**（每次升级都适用）。

> 适用：已经按旧版本部署过 TestOPS、想升级到当前版本的用户。
> **数据不会丢**（脚本会先备份），但请按顺序执行。

---

## 第 0 步：先拿到升级脚本（老版本没有它）

`upgrade.sh` 是 v1.9.0 才加入的文件——**v1.8.x 的部署目录里没有**。先取脚本：

```bash
cd <部署目录>
mkdir -p deploy 2>/dev/null
curl -fsSL https://gh-proxy.com/https://raw.githubusercontent.com/qsumm/TestOPS/main/deploy/upgrade.sh -o deploy/upgrade.sh
curl -fsSL https://gh-proxy.com/https://raw.githubusercontent.com/qsumm/TestOPS/main/deploy/wait-ready.sh -o deploy/wait-ready.sh
chmod +x deploy/upgrade.sh deploy/wait-ready.sh
```

> GitHub 直连可达的话也可以不走加速：`git fetch origin && git show origin/main:deploy/upgrade.sh > deploy/upgrade.sh`。
> 完全断网的机器：下载新版压缩包覆盖代码目录（**保留 .env 与 deploy/wheels/**），再执行。
> 校验：`head -1 deploy/upgrade.sh` 应显示 `#!/usr/bin/env bash`。
>
> **拷贝部署（没有 .git）的机器**：拿不到脚本时也可以整体换——见下方「非 git 部署：用 --code-tar 升级」。

---

## 一条命令

```bash
cd <你的测试平台部署目录>
bash deploy/upgrade.sh
```

脚本会依次做：**备份数据卷 → 检查口令兼容性 → 拉新代码 → 重建启动 → 等就绪**，
最后打印访问地址。全程 3~5 分钟（含首次构建）。

> 没有 `deploy/upgrade.sh`（老版本没这个文件）？见下面「老版本没有脚本怎么办」。

---

## 非 git 部署（拷贝部署）：用 --code-tar 升级

如果你的部署目录**不是 git 仓库**（当初用压缩包/scp 拷贝部署），`git pull` 那条路不存在。
在**有网的机器**上打包新版本代码并上传到服务器，然后：

```bash
cd <部署目录>
bash deploy/upgrade.sh --code-tar /path/to/testops-code.tgz
```

脚本会把新代码解包到 `/root/TestOPS-upgraded-<时间戳>/`、**沿用你的 `.env`**（口令/密钥/端口定制全部保留）、
备份数据卷后从新目录重建启动——数据卷同名，历史数据不丢。

代码包的打包方法（有网机器上，仓库根目录执行）：

```bash
COPYFILE_DISABLE=1 tar --exclude='.git' --exclude='._*' --exclude='docs/部署与升级/videos' -czf testops-code.tgz .
```

## 「当前版本 v1.8.1」是什么意思（两个版本别混淆）

升级输出里的「当前版本」读的是**磁盘上代码目录**的 `VERSION` 文件——不是正在运行的容器版本。
两者可能不同步（比如容器镜像之前构建自更新的代码），**这不是错误**：

| 名字 | 从哪读 | 什么时候看 |
|---|---|---|
| 代码目录版本 | 部署目录的 `VERSION` 文件 | 升级脚本的「当前版本」/「新版本」两行 |
| 运行容器版本 | `curl http://127.0.0.1:8848/api/health` 的 `version` 字段 | 升级**完成后**验收 |

升级的过程就是把两者**都对齐到 1.9.0**：第 3 步更新代码目录，第 4 步用新代码重建容器。
所以即使 `health` 已经显示 1.9.0，只要代码目录还是 v1.8.1，就**要跑完整个升级**——
否则下次重建容器会退回旧代码。

## 升级会改变什么

| 项 | 说明 |
|---|---|
| **数据** | 保留。历史指标、告警、事件、案例、用户都在 `seekdb-data` 卷里 |
| **管理员口令** | **沿用旧库**，不会被重置 |
| **数据库结构** | 自动迁移（只新增，不破坏）——新增 `alert_rules.algorithm` 的 `forecast` 值等 |
| **Agent** | 平台侧接入协议向后兼容，**老 Agent 可继续上报**；想用新能力再重跑安装命令 |
| **新增功能** | 磁盘容量预测、用户管理（系统设置 → 用户）、批量接入令牌、大盘性能修复 |

## 实测记录：脚本在真机升级模拟中修掉的 4 个坑

以下都是**真机模拟老版本升级**时暴露的（2026-11-13，CentOS Stream 9 / 受限出网环境）：

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | `git pull` 失败后脚本继续往下走，**版本号仍是 v1.8.1**（等于没升级） | 仓库处于 **detached HEAD**（用户 checkout 过 tag），`git pull origin HEAD` 必失败 | 脚本先切回 `main` 分支再 pull；**拉取失败即中止**，不再"继续用当前代码升级" |
| 2 | 升级中途 `seekdb` **容器消失**、平台半死 | `up -d --build` 会**先删旧容器再拉镜像**，镜像拉不动（受限网络）就留下坏状态 | 拆成「先 build + pull 镜像 → 最后 up -d」，失败时**旧容器仍活着** |
| 3 | `git pull` 报 `untracked working tree files would be overwritten` | 你把下载的 `upgrade.sh` 放进 `deploy/`，而新版代码里**同名文件**存在 | stash 条件补上**未跟踪文件**（原来只查 modified） |
| 4 | 本地改过 compose（端口/镜像源）→ `git pull` 被拒 | 未提交改动与新版冲突 | 同样先 stash，收尾提示 `git stash pop` 恢复；并建议把端口/镜像源等定制**挪进 `.env`**（`.env` 不受升级影响） |

> 教训：老版本部署的 compose 里写死了 `FROM python:3.11-slim`（官方源）与 `deb.debian.org`，
> 国内基本拉不动 —— **升级到 v1.9.0 后不再需要 apt 源，且镜像源可用 `.env` 覆盖**
> （`BASE_IMAGE` / `SEEKDB_IMAGE`），受限网络也能构建。

## 三个必须知道的坑（脚本已处理，但你要理解）

### ① SeekDB 的数据目录会随镜像版本变化

```
老镜像：--data-dir=/var/lib/seekdb/store      → 数据在 /var/lib/seekdb
新镜像：--base-dir=/var/lib/oceanbase         → 数据在 /var/lib/oceanbase
```

新版本 compose **两个路径都挂同一个卷**，所以升级后数据仍在。但如果你手工改过
compose 的挂载路径，升级前请确认。

### ② `SeekDB.Password.Incorrect` 无限重启

现象：`docker logs aiops-seekdb` 反复打印

```
SeekDB.Password.Incorrect: The root password is incorrect
Agent.Daemon.StartFailed: Daemon start failed: obshell server exited with code 28
```

原因：`start.sh` 用 `/var/lib/oceanbase/.initialized` 判断"是否已初始化"，而这个标记在
**容器可写层**、数据在**卷**里 —— 两者不同步时，它会以为已初始化、拿**新密码**去校验
**旧数据**，于是永远失败。

两种解法：

```bash
# a) 换回旧的口令（推荐：数据保留）
#    把 .env 里的 DB_PASSWORD 改回**升级前用的那个值**，然后
docker compose --env-file .env -f deploy/docker-compose.yaml up -d

# b) 数据不要了，清库重来
bash deploy/upgrade.sh --reset-db
```

> 另注：`DB_PASSWORD` 建议用**纯字母数字**。带 `-` `_` 等符号时部分版本解析异常。

### ③ 拉不到新代码（GitHub 不通）

```bash
# 方式一：镜像加速
git clone https://gh-proxy.com/https://github.com/qsumm/TestOPS.git
# 方式二：把新版本代码覆盖到部署目录（**保留 .env 与 deploy/wheels/**），再跑 upgrade.sh
```

## 老版本没有 `upgrade.sh` 怎么办

手工三步等价操作：

```bash
cd <部署目录>

# 1) 备份数据卷
VOL=$(docker volume ls -q | grep -i seekdb | head -1)
docker compose --env-file .env -f deploy/docker-compose.yaml stop seekdb
sudo tar czf /root/testops-backup.tar.gz -C /var/lib/docker/volumes/$VOL/_data .

# 2) 更新代码（保留 .env）
git pull            # 或重新 clone 后把 .env 拷回来

# 3) 重建启动（迁移自动执行）
docker compose --env-file .env -f deploy/docker-compose.yaml up -d --build
docker logs -f aiops-platform | grep -E "平台就绪|初始密码"
```

> 如果第 3 步 seekdb 反复重启并报 `Password.Incorrect`，按上面 ② 的两种解法处理。

## 升级后验证

```bash
curl http://127.0.0.1:8848/api/health
```

期望：`{"code":0,...,"status":"up","version":"1.9.0"}`

再进界面确认：

- `系统设置 → 用户`（新）——可以给同事开 `member` 账号
- `主机管理 → 接入新主机`——可选「本次接入机器数量」，一次签发多枚令牌
- `告警规则` 的检测算法里多了「容量趋势预测」（表达式 `>90@7d`）

## 回滚

```bash
cd <部署目录>
docker compose --env-file .env -f deploy/docker-compose.yaml down
docker volume rm $(docker volume ls -q | grep -i seekdb | head -1)
docker volume create <原卷名>          # 或直接解压备份到新卷
sudo tar xzf /root/testops-backup.tar.gz -C <卷挂载点>
git checkout <旧版本 tag>
docker compose --env-file .env -f deploy/docker-compose.yaml up -d --build
```

> 数据库迁移只做了「加列/加枚举值」，旧版本代码在新库上仍可运行——这是刻意保持的兼容性。
